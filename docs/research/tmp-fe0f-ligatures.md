## 1. Lookup: FE0F is stripped from the processing array BEFORE ligature matching
TextMeshProUGUI.cs (TextMeshPro.cs has the same code at 1718-1731 / 1737-1798):
- 1929: nextCharacter = textProcessingArray[i+1].unicode.
- 1932: emoji fallback route (IsEmoji(base) && next==FE0F, or presentation form).
- 2030-2047 VARIATION SELECTOR region: if nextCharacter is FE00-FE0F or E0100-E01EF: GetGlyphVariantIndex(base, vs); then `textProcessingArray[i + 1].unicode = 0x1A; i += 1;` (2044-2045). FE0F is overwritten with 0x1A (consumed marker; skipped later at TMP_Text.cs:2749) and i advances onto it.
- 2049-2120 LIGATURES region, runs after, only if `ligature` (2050, liga in m_ActiveFontFeatures, 1824). Lookup by first glyph: m_LigatureSubstitutionRecordLookup.TryGetValue(character.glyphIndex) (2050). Match loop 2063-2093: idx = i+1; for each remaining component, codepoint = array[idx].unicode; glyphIndex = GetGlyphIndex(codepoint); if glyph != expected AND codepoint is ignorable (TMP_TextParsingUtilities.IsIgnorableForLigature, TMP_TextParsingUtilities.cs:172-178: ZWJ, FE00-FE0F, E0100-E01EF) it is skipped (2076-2080); exact glyph match advances (2083-2088); else mismatch (2091). Trailing ignorable consumed at 2099-2100.
- Consequence: for base FE0F ZWJ second, the array seen by the matcher is [base(i), 0x1A(FE0F), ZWJ, second]. i already points at the 0x1A slot, so idx starts at ZWJ. A record whose component[1] is FE0F: ZWJ is not the expected glyph but is ignorable -> skipped; then `second` vs expected FE0F glyph -> mismatch -> no substitution. FE0F can never match because it was replaced before the match and skipped over by i+=1. Hands' hypothesis (FE0F dropped before matching) is confirmed by this source. A skip rule exists for extra ignorables but nothing inserts a missing expected component.
- ZWJ: no special handling beyond being ignorable-skippable (2076); 0x200D appears in TMP_Text.cs:2397,3070 only as the `<zwj>`-style tag replacement. FontAsset's synthesized-ZWJ line is commented out (TMP_FontAsset.cs:1102-1103).

## 4. What would make them match (options as facts; Self decides)
Matcher requires, for component FE0F, a FE0F in the array after the base; the VS block (2030-2047) removes it first whenever next is FE00-FE0F. So a match needs either
 a. records without FE0F at index 1: [base, ZWJ, second(, FE0F)] -> same ligature glyph, added to the font's GSUB (fetch_emoji_font.py / Linux container, option font-add-fe0f-less-records) or added to Emoji.asset's m_LigatureSubstitutionRecords by hand (dynamic asset: ClearFontAssetData clears the table, 3537-3539, and refetch is from the TTF, so manual records would not persist unless the asset or TTF carries them); the trailing FE0F of 1F575/1F3CC/26F9/1F3CB variants is optional because 2099-2100 consume one trailing ignorable and a trailing FE0F component (index 4) would still match as a literal; or
 b. text preprocessing that gives TMP a form its matcher can match (strip the FE0F at index 1 of those 13 before the text reaches TMP; or ITextPreProcessor, P\ITextPreProcessor.cs exists); or
 c. patching the VS block so it does not consume FE0F when a ligature record expects it (needs a package fork; ugui is "builtin" and stock-identical to the editor install); or
 d. accept the 13. There is no TMP setting that changes this path (emojiFallbackSupport only governs the font route at 1932).
Note a pure text-side strip (b) leaves base+ZWJ+second, which matches only if FE0F-less records exist (a) — Twemoji has none for these 13. So (b) alone does not work with the current TTF; (a) or (c) is required, (b)+(a) or (c) alone fixes it.
