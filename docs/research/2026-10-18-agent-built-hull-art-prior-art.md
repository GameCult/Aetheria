## A. LLM and agent driven 3D modelling

### A1. Systems and what they report

- **LL3M** (Chen et al., arXiv 2508.08228, Aug 2025): plan / retrieve / write / critique / verify agents writing Blender Python; a retrieval base over Blender API docs (BlenderRAG). https://arxiv.org/html/2508.08228v1 (read via WebFetch). Models: GPT-4o planner and retrieval, Claude 3.7 Sonnet coder, Gemini 2.0 Flash critic (Sec. 4.1; Appendix A.2 lists GPT-4o for critic, the paper does not reconcile the two). Repo https://github.com/threedle/ll3m notes the server is discontinued (search-summary).
  - Quantitative evidence is one table: errors per run 2.43 with RAG versus 3.29 without, 17 objects (Table 1). Agent ablation (Fig. 16) and shared-code-context ablation (Fig. 17) are qualitative, single examples.
- **BlenderGym** (Gu et al., CVPR 2025, arXiv 2504.01786): 245 start/goal scene pairs over object placement, lighting, procedural material, blend shape and procedural geometry editing. https://arxiv.org/abs/2504.01786 (abstract read), https://openaccess.thecvf.com/content/CVPR2025/html/Gu_BlenderGym_Benchmarking_Foundational_Model_Systems_for_Graphics_Editing_CVPR_2025_paper.html (search-summary). Abstract: even the strongest VLM system struggles on tasks "relatively easy for human Blender users"; scaling the verifier helps, and compute is better split between generation and verification. Models tested were GPT-4o, Claude 3.5 Sonnet, Gemini 1.5 Flash, InternVL2-8B, Qwen2-VL-7B (search-summary). The PDF fetch returned binary; per-task scores were not read.
- **BlenderAlchemy** (Huang, Yang, Guibas, ECCV 2024, arXiv 2404.17672): VLM edit generator plus state evaluator searching edits to procedural materials, geometry and lighting; uses reference images from image generators to ground text. https://arxiv.org/html/2404.17672v1 (search-summary; benchmark numbers not read).
- **SceneCraft** (Hu et al., ICML 2024, arXiv 2403.01248): scene graph as blueprint, spatial relations turned into numerical layout constraints, VLM render inspection, and a growing library of reusable script functions. https://proceedings.mlr.press/v235/hu24g.html (search-summary).
- **3D-GPT** (arXiv 2310.12945): dispatch / conceptualization / modeling agents driving Infinigen procedural generators. https://arxiv.org/html/2310.12945v2 (search-summary). SceneCraft's paper is reported to say 3D-GPT's reliance on Infinigen limits it on large scenes and that diversity is limited by prompt expressiveness (search-summary, second-hand).
- **CADCodeVerify** (arXiv 2410.05340, ICLR 2025): VLM asks and answers validation questions about its own CAD render, then corrects. On CADPrompt (200 prompts) reports a 7.30% point-cloud-distance drop and 5.5% compile-rate gain for GPT-4; off-the-shelf models "hallucinate on complex, out-of-distribution tasks". https://arxiv.org/html/2410.05340v2 (search-summary).
- **Text2CAD-Bench** (arXiv 2605.18430): execution success does not guarantee geometric correctness; sweep, loft and shell cause widespread execution failures. https://arxiv.org/pdf/2605.18430 (search-summary).
- **Text2CAD** (arXiv 2409.17106): ~1% invalid outputs; discrepancy from prompt greatest when prompts name objects instead of giving dimensions (search-summary).
- **CAD-Recode** (Rukhovich et al., ICCV 2025, arXiv 2412.14042): point cloud to CadQuery Python via a Qwen2-1.5B decoder trained on one million synthetic CAD programs; reports ~10x lower mean Chamfer than prior work on DeepCAD and Fusion360. https://huggingface.co/papers/2412.14042 (search-summary). It reconstructs from a scan; it does not invent shapes from text.
- **ShapeAssembly** (Jones et al., SIGGRAPH Asia 2020, arXiv 2009.08026): a DSL of cuboid part proxies with attachment operators and symmetry macros; generated by a hierarchical VAE, not an LLM. https://arxiv.org/abs/2009.08026 (search-summary). A search for LLM plus ShapeAssembly-style cuboid programs returned nothing.
- **build123d-mcp** (PyPI): claims that rendering views and checking dimensions during the build lifts GPT-5.5 from 0.360 to 0.457 on CADGenBench and validity from 88% to 100%; the author's own claim, leaderboard not verified. https://pypi.org/project/build123d-mcp/0.3.70/ (search-summary).

### A2. Failure modes documented

From LL3M (https://arxiv.org/html/2508.08228v1, read):
- Non-executing code is the main documented failure (Sec. 3.1); without retrieval the coder "solves" errors by deleting the offending lines (App. D).
- Spatial placement: the critic and verifier can miss spatial problems; the limitations section shows watering-can handles disconnected or wrongly posed (Sec. 5, Fig. 18); an ice cream in a hand needed several follow-up prompts (Sec. 4.4, App. E).
- Disconnected parts in first outputs (Fig. 5, Sec. 3.2); a bucket first came out a plain cylinder until refined (Sec. 4.2).
- Symmetry and interpenetration are not discussed explicitly by the paper.

From CAD-code work: valid-but-wrong geometry (Text2CAD-Bench, CADCodeVerify, above); numeric checks can pass while the render looks wrong (cc-blender-skill README, C3).

Internal measurement on the same question (Opus, own tools): see Internal fit section "Mesh probe runs" for chamfer, silhouette-IoU and which parts of the loop contributed.

## B. Primitive and grammar approaches to ships

### B1. Procedural ship generators

- **a1studmuffin/SpaceshipGenerator** (MIT): start from a box; repeatedly extrude front and rear faces with random translate/scale/rotate; extrude random faces with shrinking scale for asymmetry; classify faces by orientation and add engines, antennae, turrets, lights; optional mirror; Bevel modifier; global-space cube UVs plus a greeble normal map and emissive window maps; seeded. README gives no parameter values or orientation rules; those are in `spaceship_generator.py`. https://github.com/a1studmuffin/SpaceshipGenerator (read). Forks: panzi, ldo, David-Kasilia (search-summary). A paid Geometry Nodes alternative exists on Blender Market (search-summary).
- **Kinnear and Kaplan**, "Procedural generation of surface detail for science fiction spaceships", Computational Aesthetics 2010: https://cs.uwaterloo.ca/~csk/publications/Papers/kinnear_kaplan_2010.pdf. Already read in full by the earlier greebles pass: GameCult.Geometry.Csg `docs/research/greebles-prior-art.md` section 2 (commit 4877300, branch origin/eureka/brush-tree). Not repeated here.

### B3. What makes low poly read as deliberate (practitioner opinion, no controlled study found)

- https://bugnet.io/blog/low-poly-3d-a-style-guide-for-small-teams (search-summary): commitment is the dividing line; smoothing groups over low geometry gives a "cheap mobile game" impression; silhouette carries the read once interior detail is stripped, exaggerate proportions; set facet density per asset class and keep it even across the scene; a shared palette (often one small palette texture) unifies assets; flat shading is the style's signature; harsh light transitions on flat faces are mitigated with subtle vertex colour.
- https://gamedeveloper.com/design/how-to-make-low-poly-look-good and https://rocketbrush.com/blog/low-poly-art-in-games (listed by search, not read).
- The vendor claim that a stylized look reads as intentional while a half-finished photoreal one looks broken is from a vendor page (summerengine.com) and is marketing.
- Internal operator statement on look: `aetheria-release:ruling:panel-lines-are-geometry` and the shippable bar (Internal fit) describe the operator's own finishing standard (one-segment bevel, face-weighted normals); nothing in the mind rules a low-poly flat-shaded style for Aetheria.

## C. Skill and prompt packs for 3D work
