# Cut 7 (Roles Authored): Operator Review

Generated by `dotnet run --project tools/AetherDb -- roles-migrate` (dry run captures this exact table; `apply`
landed it in `GameData/Aetheria.cc`). Regenerate with `roles-migrate` any time the catalog changes — this file is
a snapshot for review, not a second source of truth.

Role vocabulary is small and shared within a kind: the same handful of part names cover every design of that
kind, not one bespoke name per item. A stat is only pointed at a role when it both carries a `Quality` term and
actually varies with quality (`Min != Max`) — Cut 1's flat placeholder stats (`Min == Max`, a harmless leftover
`Heat^1` term) have no observable role-vs-workmanship difference, so pointing a role at one would be authoring
fiction, not content.

Product role means below are almost all **generic placeholders** (deterministic per product+role, not hand-tuned)
flagged "needs operator review" — the one exception is Arctica/Alakrita, where `docs/item-provenance-target.md`
already states a brand identity ("optimizing for heat efficiency"). Every other product is waiting on the
operator to decide who is actually good at what; right now they only differ from each other by an arbitrary seed,
not by authored intent.

## O7 — what the operator should actually do with this

Everything above the "generic — needs review" line is mechanically correct (verified: `census`'s new
"(product, role) pairs where a sold, role-bearing design authors no matching spread" check reports 0, and two
products of one design with different means resolve a role-termed stat to different, deterministic values —
`RoleAuthoringTests.TwoProductsOfOneDesignWithDifferentRoleMeansResolveDifferentValues`). What it is *not* is
real market segmentation: every design still has exactly one product, so nothing yet demonstrates "a second
product with a role pumped up." That is next scope, and it needs the operator's judgment on which manufacturer
is good at what — this table is the jumping-off point, not the destination.
